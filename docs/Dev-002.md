# Dev-002: Persistent character memory (perfect recall, template-based)

[Feature] [Engine] [DB] [Narrator] [Data]

Events are already stored with their witnesses, but nothing a character lived survives as something
the narrator, or a future NPC decision, can consult. This DEV derives per-character memories from
witnessed events and gives the narrator a bounded, ranked selection of Niko's memories in its
prompt. Version 1 uses perfect (non-fallible) memory, template text instead of LLM summaries and no
embeddings, so the change is deterministic, costs nothing to run and can be tested offline.

## 3. Scope

### 3.1 Schema

One new table, created by the next numbered migration (append-only, no savegame wipe). The foreign
key must point at the real events table name.

```sql
CREATE TABLE memories (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  character_id TEXT    NOT NULL,
  event_id     INTEGER NOT NULL REFERENCES events(id),
  tick         INTEGER NOT NULL,
  zone_id      TEXT    NOT NULL,
  text         TEXT    NOT NULL,
  importance   INTEGER NOT NULL CHECK (importance BETWEEN 1 AND 10),
  participants TEXT    NOT NULL,  -- JSON array of character ids involved in the event
  UNIQUE (character_id, event_id)
);
CREATE INDEX idx_memories_character_tick ON memories (character_id, tick DESC);
```

The `UNIQUE` constraint makes memory creation idempotent per witness and event.

### 3.2 Memory creation

- After the engine commits an event, it creates one memory for each witness of that event. A
  character that did not witness the event gets nothing, which enforces "reactions come from
  knowledge".
- `memoryFromEvent(event, witnessId)` is a pure function that builds the text from a template per
  event kind (short sentences, no decoration, matching the narrator style). No LLM call is made.
- Importance comes from `data/memory_rules.json`, keyed by event kind. Unknown kinds default to 2,
  so a new event kind never breaks memory creation.
- Memories are never updated or deleted by game code (perfect memory).

### 3.3 Recall

`recall(characterId, query, limit)` returns memories ranked by a score, where `query` holds the
current tick, zone, characters present and optional keywords.

```
score = 0.4 * recency + 0.4 * (importance / 10) + 0.2 * relevance
recency   = 0.5 ^ ((nowTick - memory.tick) / HALF_LIFE_TICKS)
relevance = (sameZone + sharesParticipantWithPresent + keywordMatch) / 3
```

- Each relevance term is 0 or 1. Weights and `HALF_LIFE_TICKS` (provisional: 50) live in
  `data/memory_rules.json`.
- Ties are broken by higher `id` first, so the order is total and reproducible.
- Recall uses no RNG and no wall-clock time.
- Scores are rounded to 6 decimals before comparing, so the order does not depend on float noise.

### 3.4 Narrator prompt

- `OpenRouterNarrator` adds a block "Niko's memories", filled from `recall` for Niko.
- The block is capped by `promptMaxItems` (provisional: 8) and `promptMaxChars` (provisional: 1200),
  both in `data/memory_rules.json`. When over budget, the lowest-ranked memories are dropped first.
- Selected memories are printed in chronological order, one line each: `t{tick}: {text}`.
- `OfflineNarrator` is unchanged. A narrator failure or bad JSON still falls back to offline.

## 4. Decisions

- **Decided (from brainstorming):** perfect memory in v1, turn-based, Niko is the only controlled
  character.
- **Decided (from brainstorming):** all LLM traffic goes through OpenRouter; no VPS.
- **Proposed, needs approval:** template text instead of an LLM summary per memory. Reason: zero
  cost, deterministic, testable offline. Revisit when memories need richer wording.
- **Proposed, needs approval:** store a memory for every witnessed event, including low-importance
  movement, and let recall ranking and the prompt budget filter. Alternative: skip events below an
  importance threshold, which keeps the table small but breaks "perfect".
- **Proposed, needs approval:** scoring weights, `HALF_LIFE_TICKS`, `promptMaxItems` and
  `promptMaxChars` are provisional and tunable in data without code changes.

## 5. What must not break

- The engine is the only writer of state; `memory.ts` is called by the engine and never by the
  narrator or the client.
- The single `Action` API is untouched; no actor gets a memory shortcut.
- The client never simulates and does not need any change.
- Determinism: same seed and same commands produce the same memory rows and the same recall order;
  no `Math.random` and no `Date.now` inside the simulation, randomness only through `rngFor`.
- Migrations stay append-only and apply cleanly on an existing `game.db`.
- The narrator proposes, the engine decides; the offline mode keeps working with no network.
- `llm_calls` keeps logging every call with tokens and cost.

## 6. Acceptance

Verification in `test/memory.test.ts` unless stated otherwise.

- The new migration applies on a database at the previous schema version and keeps existing rows.
- Only witnesses get a memory: for an event seen by Niko and not by an NPC, the NPC has none.
- Same seed and same command sequence give identical `memories` rows across two fresh runs.
- After a fixed number of ticks, each character's memory count equals the events they witnessed.
- `recall` orders by score, breaks ties by higher `id`, respects `limit` and returns an empty list
  for a character with no memories.
- Unknown event kinds get the default importance and still create a memory.
- `test/narrator.test.ts`: the OpenRouter prompt contains the memory block within `promptMaxItems`
  and `promptMaxChars`, and the offline narrator output is unchanged.

## TL;DR

Add a `memories` table, create one template-based memory per witness of each committed event, rank
them with a deterministic recency, importance and relevance score, and feed a capped selection of
Niko's memories to the OpenRouter narrator. Memory is perfect, costs no LLM calls and is verified
by `test/memory.test.ts`, `test/narrator.test.ts`, `npm run check` and one manual OpenRouter run.
