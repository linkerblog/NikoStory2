# Dev-008: Items, inventory and the first scene goal

[Feature] [Engine] [World] [Narrator] [Client] [Data] [DB] [Migration]

The world can be explored, talked to and narrated, but nothing in it can be picked up and nothing the
player does can finish anything. Ivy's agenda talks about a letter on the kitchen table that does not
exist as a thing, the interpreter is told it may `open` and `take` while the engine turns every
`interact` into `examine`, and the scene question in `data/scene.json` has no way to be answered.
This DEV adds portable items with a single owner (a tile or a character), four item verbs the engine
resolves (`take`, `drop`, `search`, `read`), reading as a second way to learn a fact, and a data-driven
scene goal the engine marks resolved when Niko knows every required fact. The result is the first
complete loop: explore, find, read, talk, resolve.

## 2. Findings / current state

Measured in the current tree.

- **Verbs are promised but not kept.** `interpreterPrompt` in `src/interpreter.ts` advertises
  `"verb":"examine|open|take"`; `sanitizeEffect` accepts any string; `Engine.applyEffect` in
  `src/engine.ts` maps every `interact` to `{ type: "examine" }`. "Take the letter" is narrated as an
  examine with no error, which breaks the "rejected with a reason" contract in `AGENTS.md`.
- **There are no items.** Zone `objects` (`Obj` in `src/world.ts`) are furniture: static, stored as
  JSON inside the `zones` row, with no owner. Nothing can move between a tile and a character.
- **Facts come only from conversations.** `closeConversation` is the only writer of `facts_known`.
  `fact_ivy_letter` says the letter is on the kitchen table, but there is no letter to find.
- **The scene has a question and no end.** `data/scene.json` has `question` and `facts`; the engine
  sends `knownFacts` to the narrator and nothing ever checks whether the question is answered.
- **The client advertises an inventory it does not have.** The help overlay in `public/index.html`
  lists `g` then `i` for "Inventory"; no inventory panel or section exists.
- The offline parser in `src/actions.ts` treats `search`, `open` and `read` as `examine`. Tests in
  `test/interpreter.test.ts` and `test/memory.test.ts` send "open the crate" / "open the ghost".

## 3. Scope

### 3.1 Items table (migration 7)

Append to `MIGRATIONS` in `src/db.ts`:

```sql
CREATE TABLE items (
  id        TEXT PRIMARY KEY,
  name      TEXT NOT NULL,
  zone_id   TEXT,
  x         INTEGER,
  y         INTEGER,
  holder_id TEXT,
  hidden    INTEGER NOT NULL DEFAULT 0,
  data      TEXT NOT NULL DEFAULT '{}',
  CHECK ((holder_id IS NULL) <> (zone_id IS NULL))
);
```

- An item is in exactly one place: on a tile (`zone_id`, `x`, `y`) or held (`holder_id`). The
  `CHECK` makes a duplicated or lost item a database error, not a narration bug.
- Items never block movement and may share a tile with furniture: the letter sits on the table's
  tile, reached from an adjacent tile like `examine`.
- `hidden = 1` means the item is on that tile but not perceived until someone searches the object
  there. `data` holds `description`, `portable`, and for readable items `text` and `reveals`.
- `clearSave` deletes `items` before `entities`.

### 3.2 Data and seeding

- `data/items.json`, validated on load like `rules.json` (unknown zone, a tile outside the map, a
  `reveals` id missing from `data/scene.json` or a duplicate id is an error):

```json
[
  { "id": "letter", "name": "a letter addressed to Niko", "zone_id": "house_001", "x": 6, "y": 3,
    "data": { "portable": true, "description": "A folded sheet with Niko's name on the front.",
              "text": "<authored by the user>", "reveals": "fact_letter_text" } },
  { "id": "house_key", "name": "a spare key", "zone_id": "house_001", "x": 8, "y": 8, "hidden": 1,
    "data": { "portable": true, "description": "A small brass key." } }
]
```

- `fact_letter_text` is added to `data/scene.json` with `"revealed_by": "letter"`.
- `seedItems(db, dataDir)` runs from `src/game.ts` on every load: `INSERT OR IGNORE` per id, guarded
  by a `items_seeded` settings key, so a v0.6.0 save gains the letter once and a later `take` is never
  undone by a restart. Generated buildings get no items in this DEV.

### 3.3 Action API

- Add to the `Action` union in `src/actions.ts`:
  `{ type: "item"; verb: ItemVerb; target: string }` with `type ItemVerb = "take" | "drop" | "search" | "read"`.
  `search` targets an object id; the other three target an item id.
- `parseFreeAction` maps `take|grab|pick up|get` → `take`, `drop|put down` → `drop`,
  `search|open` → `search` (on an object), `read` → `read`; `examine|inspect|check|study|look`
  stays `examine`. Name matching works like today's object matching, over visible and held items.
  "Open the crate" becomes a `search` that finds nothing and still succeeds, so the existing tests
  keep their meaning.
- `actionToEffects` maps `item` to `{ kind: "interact", target, verb }`.

### 3.4 Engine resolution

`applyEffect` dispatches `interact` by verb: `examine` keeps today's path; the four item verbs go to
`applyAction({ type: "item", ... })`; any other verb is **rejected** with "Niko cannot do that with
it." instead of silently becoming an examine. One verb = one effect = one tick, as today.

| Verb | Preconditions (else rejected with a reason) | Result | Event |
|---|---|---|---|
| `take` | item in Niko's zone, not hidden, `near(niko, item)`, `portable`, held count `< rules.inventorySlots` | `holder_id = 'niko'`, tile cleared | `take` |
| `drop` | item held by Niko | placed on Niko's tile | `drop` |
| `search` | object in zone and `near` | every hidden item on that object's tile gets `hidden = 0` | `search` with `found: [ids]` |
| `read` | item held or `near`, not hidden, has `text` | `reveals` written to `facts_known` for `'niko'` (`INSERT OR IGNORE`) | `read` with `fact_id` |

- All four go through `record()`, so witnesses are vision plus line of sight like every event.
  Witnesses learn that Niko read something, not what it said: only Niko's `facts_known` changes.
- `rules.inventorySlots` is added to `data/rules.json` (provisional `8`) and validated in
  `src/rules.ts` as a positive integer with that default.
- Search is deterministic (it always finds what is there). No roll is needed; when a skill check is
  added later it goes through `rngFor` like `ability`.
- NPCs are unchanged: `applyNpcEffect` keeps examine-only `interact`, and an NPC item verb is
  rejected so the `npc` role cannot move items yet ([Sec. 8]).

### 3.5 Interpreter

- `InterpretContext` gains `items: { id; name; where: "held" | "here" }[]`: Niko's inventory plus
  non-hidden items in his zone that he `canSee`. Hidden items are never sent, so the model cannot
  take what nobody has found.
- The prompt's line becomes
  `{"kind":"interact","target":"<object or item id>","verb":"examine|search|take|drop|read"}`.
- `sanitizeEffect` lowercases `verb`, maps `open` → `search` and `grab`/`pick_up` → `take`, and keeps
  any other value as given so the engine rejects it with a reason ([Sec. 3.4]).
- `keywordsOf` already picks item names from the text; no change.

### 3.6 Scene goal

- `data/scene.json` gains
  `"goal": { "id": "why_niko_fell", "text": "<authored by the user>", "requires": ["fact_marta_warning", "fact_letter_text"] }`,
  validated in `loadScene` (`requires` must be known fact ids). A scene with no `goal` behaves as today.
- After each successful turn (`takeTurn`, before `flushMemories`), the engine checks whether every
  `requires` fact is in Niko's `facts_known` and `scene_resolved` is unset; if so it sets
  `scene_resolved` to the tick and records a `scene_resolved` event (Niko as actor, his witnesses).
- The narrator payload's `scene` gains `goal` and `resolved`; the narrator prompt says to close the
  beat on the answer when `resolved` turns true. No next scene is loaded ([Sec. 8]).

### 3.7 State and client

- `state()` adds `inventory: { id, name }[]`, `items` (visible, non-hidden items in the zone with
  `x`, `y`) and `scene: { question, goal, known: string[], resolved }`. Only facts Niko knows are sent.
- `public/index.html`: items drawn on the map with one glyph; the Status panel gets **Inventory**
  and **Goal** sections (`g` then `i` focuses Inventory, as the help already says). The client only
  draws; clicking an item fills the command line with "take <name>" and sends nothing by itself.

### 3.8 Memory

- `data/memory_rules.json` importance: `take` 3, `drop` 2, `search` 3, `read` 6, `scene_resolved` 9.
- `memoryFromEvent` templates: "Niko took a letter addressed to Niko.", "… searched the wardrobe and
  found a spare key." / "… found nothing.", "… read a letter.", "… understood why he fell."
- `take`, `drop` and `search` join `TEMPLATE_TYPES` (no model call); `read` and `scene_resolved`
  are worded by the `memory` role with the template as fallback, like `talked`.

## 4. Decisions

- **Proposed, needs approval:** items live in their own table, not inside the zone's `objects`
  JSON. Reason: an item changes owner many times; furniture never does, and rewriting a whole zone
  row on every pickup would make two zones able to disagree about one item.
- **Proposed, needs approval:** a closed verb list (`examine`, `search`, `take`, `drop`, `read`).
  `give` and `use` wait until there is a consumer for them (a lock, an NPC that wants something).
- **Proposed, needs approval:** reading is a second writer of `facts_known`, equal to conversations.
- **Needs the user's authoring:** the letter's `text`, the wording of `fact_letter_text` and the goal
  `text`. They decide the story's answer, so the DEV ships placeholders and does not invent lore.
- **Provisional:** `inventorySlots = 8`, the spare key and the new importance values are data.

## 5. What must not break

- The engine is the only writer of state; the interpreter only proposes `interact` effects.
- One action API: item verbs are one more `Action`, reached by the client, the offline parser and
  the interpreter the same way.
- The client never simulates: inventory and goal are read from `state()`.
- Determinism: no new randomness; same seed and same actions give the same items and facts.
- Reactions come from knowledge: item events carry witnesses; hidden items reach no prompt.
- Migrations stay append-only; a v0.6.0 `game.db` opens, gains the table and the seeded items.
- Every existing test passes without edits, including "open the crate" and "open the ghost".

## 8. Out of scope

- `give`, `use`, locks, containers that hold other items, stacking and item weight.
- NPCs taking, carrying or reacting to items; NPCs reading `facts_known` (Ivy's agenda still talks
  about the letter after Niko has it).
- Items in generated buildings and architect-placed items.
- A second scene or any consequence after `scene_resolved` beyond the narration.
- Combat, health and equipment.

## TL;DR

Add portable items in their own table (one owner each, enforced by a `CHECK`), four engine-resolved
verbs (`take`, `drop`, `search`, `read`) that replace the silent "everything is examine", reading as
a second source of facts, and a data-driven scene goal that resolves once when Niko knows the
required facts. Items, inventory and the goal reach the interpreter, narrator and client through the
existing paths. Verified by a new `test/items.test.ts`, interpreter and migration tests, and
`npm run check`; the letter's text and the goal are left for the user to author.
