# Dev-007: LLM-driven NPC decisions and NPC-to-NPC conversations

[Feature] [Architecture] [Engine] [Narrator] [Data] [DB]

Today every NPC is a deterministic automaton: it pursues one authored agenda with BFS pathing and
otherwise wanders ([Sec. 2.1]), and every conversation is Niko-to-NPC and can only be opened,
advanced or closed by Niko ([Sec. 2.2]). This DEV adds an `npc` model role that proposes typed
effects for one NPC at a time, which the engine validates through the same tile, path and event
rules as any other actor, and generalizes conversations to two participants so two NPCs (or an NPC
and Niko) can hold a capped exchange the engine drives. Offline play, the spend cap and any model
failure fall back to the exact deterministic behavior that exists now, so the world stays replayable
and the current tests keep passing unchanged.

## 2. Findings / current state

Measured in the current tree.

### 2.1 NPC behavior has no model

- `src/engine.ts` [Sec. stepWorld] (around `stepWorld`) is the whole NPC brain: each tic, an NPC with
  an `active` or `blocked` agenda takes one `bfsStep` toward `goalPoint`, marks `arrived` when
  `reached`, and falls back to a seeded `wander` roll otherwise. No model call, fully deterministic.
- `src/agenda.ts` owns the agenda kinds (`approach`, `follow`, `visit`), the fixed-neighbor BFS and
  the RNG-free pathing.
- Movement already goes through `free()`, `moveTo()` and `record("move", ...)`, so an NPC cannot cut
  through a wall; there is no separate path for actors.

### 2.2 Conversations are Niko-only

- `Conversation` in `src/engine.ts` is `{ id, npc_id, goal_id, status, beat, started_tick }`; the
  schema is migration 3 in `src/db.ts`. `npc_id` is implicitly "the other side of Niko".
- `applyAction` refuses every action but `reply`/`leave` while a conversation is open, and only Niko
  reaches `talk`/`reply`/`leave`; NPCs never open one. `stepWorld` skips the NPC whose id is the open
  conversation's `npc_id`.
- `closeConversation` marks the agenda `done`, writes the agenda's `reveals` into `facts_known` for
  `'niko'`, and records a `talked` event with its witnesses.
- `conversation()` reads the newest `status = 'open'` row with no uniqueness constraint.

### 2.3 Role plumbing

- `LlmRole` and `LLM_ROLES` are in `src/llm.ts`; per-role model/reasoning/idle come from
  `<ROLE>_MODEL`/`<ROLE>_REASONING`/`<ROLE>_IDLE_MS` in `src/server.ts`; every call is logged to
  `llm_calls` with its real role. `EngineServices` in `src/engine.ts` carries `narrator`,
  `interpreter` and optional `memories`, and `offlineServices()` in `src/game.ts` builds the offline
  set.
- `record()` births each event with its `witnesses` (vision range plus line of sight), so knowledge
  stays perception-bound; `TEMPLATE_TYPES` keeps `move`/`wait`/`appears` memories free.

## 3. Scope

### 3.1 A new `npc` role

- Add `"npc"` to `LlmRole` and `LLM_ROLES`. Default reasoning on, model defaulting to
  `NARRATOR_MODEL`, idle timeout from `<ROLE>_IDLE_MS` — the existing `roleConfig` needs no special
  case beyond a `REASONING_DEFAULT` entry.
- Add `npcdecider?: NpcDecider` to `EngineServices`; `offlineServices()` leaves it unset, which is
  the fallback signal. `src/server.ts` builds `OpenRouterNpcDecider(llm)` when a key and a model are
  configured.
- The role is logged as `npc` in `llm_calls` and is switched off by the spend cap like the others.

### 3.2 `src/npc.ts`

- `NpcContext`: `actor` (id, name, personality), `agenda` (goal id, kind, want), `place` (zone id,
  name, room), `visible` (id, name, proximity, direction), `nearbyObjects`, `ether`, `rules`, the
  last few events this NPC witnessed, the open conversation it is in (if any), and `tick`.
- `interface NpcDecision { effects: Effect[]; say?: string }` and
  `interface NpcDecider { decide(c: NpcContext, onDelta?: DeltaSink): Promise<NpcDecision | null> }`.
- `OfflineNpcDecider` returns `null`; the engine then runs the existing deterministic step, so
  offline behavior is unchanged by construction.
- `OpenRouterNpcDecider` sends the payload with the prompt below and parses the reply with the
  interpreter's `sanitizeEffect` and `extractJson`, dropping malformed effects rather than guessing.
- Prompt (draft): decide one action for the named NPC, using only ids in the situation; allowed
  effects are the interpreter's (`move`, `wait`, `speak`, `end_conversation`, `interact`, `ability`);
  keep `speak.text` in the NPC's voice and language; a `move` costs at most `rules.maxPathSteps`; if
  nothing is worth doing, return `{"effects":[{"kind":"wait"}]}`.

### 3.3 Conversation participants (migration 6)

Append one migration to `MIGRATIONS` in `src/db.ts`:

```sql
ALTER TABLE conversations ADD COLUMN initiator_id TEXT;
ALTER TABLE conversations ADD COLUMN listener_id TEXT;
UPDATE conversations SET initiator_id = 'niko' WHERE initiator_id IS NULL;
UPDATE conversations SET listener_id = npc_id WHERE listener_id IS NULL;
```

- A conversation is between exactly two participants: `initiator_id` opens it, `listener_id`
  answers. Existing rows backfill to `('niko', npc_id)`, so `test/conversation.test.ts` reads the
  same state.
- `npc_id` keeps its `NOT NULL` for old rows and is no longer read by new code; new inserts set it
  to the listener to satisfy the constraint and are documented as legacy.
- Add a helper `participants(convo)` and `conversationsWith(id)`; `conversation()` is redefined as
  "the newest open conversation Niko participates in".
- Per-tick bookkeeping: the engine records on the row who acted last (`beat` remains the count), so
  a beat owned by one side is not advanced again by the other in the same tick.

### 3.4 Applying an NPC proposal

- `stepWorld` becomes `async`; its callers in `runTurn`, `freeTurn` and `fallStep` already `await`.
- The NPC loop is rewritten to: skip an NPC in an open conversation it participates in; ask the
  decider once per player turn (a per-turn `Set<string>` of NPC ids that already proposed, cleared in
  `takeTurn`) only when `tick % rules.npcThinkEveryTicks === 0` and the NPC `canSee` Niko; if the
  decider returns `null`, over budget or an error, run the current agenda/wander code untouched.
- A returned decision is applied by a new `applyNpcEffect(actor, effect, ents)` that reuses `free()`,
  the same path checks, `moveTo()` and `record()`. Effects run in order to at most `rules.maxEffects`;
  at the first rejection the sequence stops. If no effect applied the NPC falls back to its
  deterministic step, and if at least one applied the agenda does **not** also run, so a tick never
  moves an NPC twice. (Deviation from the first draft, which said "always fall back".)
- Effects that build a server-side object for Niko (portal entry, Ether spend, Niko's conversation
  lock) are not available to `applyNpcEffect`; the NPC path only moves, waits, speaks, interacts and
  ends a conversation.
- The tick advances once per player action exactly as today; the NPC decision replaces one NPC's step
  for that tick, it does not add ticks or extra events.

### 3.5 Conversations between two actors

- An NPC `speak` with `to` a visible, adjacent character opens a conversation if none exists between
  the two, otherwise advances the open one; `to: null` stays a monologue (`say`).
- An NPC-to-NPC exchange alternates: `mayAdvance` gives the listener an odd beat and the initiator an
  even one, and the opening row starts at beat 1 so the listener answers first. Only the side whose
  turn it is is asked, so a conversation cannot run away. (Added during implementation to keep one
  speaker per beat.)
- Beats are capped by `stakes.maxBeats` as for Niko; the engine closes the conversation, records the
  `talked` event with its witnesses and marks the NPC's agenda `done` when the goal was delivered.
- `closeConversation` is generalized to participants: the `reveals` fact is written to
  `facts_known` only when Niko is a participant (as today); an NPC-to-NPC exchange records the event
  and writes no fact, because NPC knowledge of facts is out of scope [Sec. 8].
- While Niko has an open conversation, his lock is unchanged: he may only answer or leave, and an NPC
  speaking to him does not bypass that lock.
- Only witnesses (vision plus line of sight) of a `talked` event get its memory, so two NPCs talking
  out of sight are not "heard" by Niko.

### 3.6 Data and prompts

- `data/rules.json`: add `npcThinkEveryTicks` (provisional `3`) alongside `maxEffects`.
- `data/npcs.json`: add an optional `voice` string per NPC (a one-line register hint) used by the
  prompt when present; absent means the personality alone is sent.
- The narrator and interpreter payloads are unchanged except where the generalized conversation
  fields already flow through.

## 4. Decisions

- **Proposed, needs approval:** a dedicated `npc` role rather than extending `interpreter`. Reason:
  different cadence, different cost profile and a per-role model, as the architecture requires.
- **Proposed, needs approval:** one NPC proposal per player turn at most, gated by visibility and
  `npcThinkEveryTicks`, to bound cost and latency. Alternative: one proposal per NPC per tick (more
  alive, far more calls).
- **Proposed, needs approval:** conversations gain two explicit participants additively; the legacy
  `npc_id` column stays as a write-through for `NOT NULL`. Alternative: a new `conversation_participants`
  table (cleaner but a larger change with no behavior difference yet).
- **Proposed, needs approval:** NPC-to-NPC conversations do not write `facts_known`.
- **Provisional:** `npcThinkEveryTicks = 3` and the `voice` hint are data, tunable without code.

## 5. What must not break

- The engine is the only writer of state; the `npc` role proposes effects and writes nothing.
- The single `Action` API: an NPC proposal goes through the same `free()`/path/witness checks as
  Niko; no actor gets a private shortcut through walls.
- Determinism and offline: with `offlineServices()` the world is byte-identical to today, and the
  existing agenda tests must pass without edits. Risk stays in `rngFor`; no wall-clock time.
- Reactions come from knowledge: witnesses and `canSee` are unchanged; an NPC only sees what its own
  range and line of sight allow.
- Migrations stay append-only and apply on an existing `game.db`.
- `llm_calls` logs every call with its real role; the spend cap disables the `npc` role too.
- The client never simulates; no client change is required.

## TL;DR

Give NPCs a dedicated `npc` model role that proposes typed effects for one actor at a time, applied
by the engine through the same tile, path and witness checks, with the deterministic agenda as the
offline and over-budget fallback; generalize conversations to two participants with one append-only
migration so NPC-to-NPC exchanges are capped and closed by the engine. Verified by a new
`test/npc.test.ts`, the unchanged conversation tests, a migration test and `npm run check`.
