# Dev-003: Stakes — NPC agendas, real conversations and a sharper narrator

[Feature] [Engine] [World] [Narrator] [Data] [DB]

A sample playthrough reads as flat: NPCs only wander, so the narrator has nothing to tell except
positions; the same "Marta appears, serious" beat repeats across turns; distances are reported in
tiles; and a conversation with Marta is summarized in one line instead of being played. This DEV
gives NPCs simple agendas (they want something from Niko), turns talking into a short multi-turn
exchange, adds one scene hook that conversations reveal, and tightens what the narrator is asked to
write. It builds on the memory added in Dev-002 and keeps every rule deterministic and offline-safe.

## 3. Scope

### 3.1 Schema

One migration (append-only). Table and column names must match the existing events and characters
tables.

```sql
CREATE TABLE agenda_state (
  character_id TEXT PRIMARY KEY,
  goal_id      TEXT NOT NULL,
  status       TEXT NOT NULL CHECK (status IN ('active','arrived','done','blocked')),
  since_tick   INTEGER NOT NULL
);
CREATE TABLE conversations (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  npc_id       TEXT    NOT NULL,
  goal_id      TEXT    NOT NULL,
  status       TEXT    NOT NULL CHECK (status IN ('open','closed')),
  beat         INTEGER NOT NULL DEFAULT 0,
  started_tick INTEGER NOT NULL
);
CREATE TABLE facts_known (
  character_id TEXT    NOT NULL,
  fact_id      TEXT    NOT NULL,
  tick         INTEGER NOT NULL,
  PRIMARY KEY (character_id, fact_id)
);
```

### 3.2 NPC agendas

- Each NPC in `data/` gains an agenda: `goal_id`, a `kind`, a target and a short `want` sentence
  the narrator can use.

```json
{ "goal_id": "marta_warn", "kind": "approach", "target": "niko",
  "want": "Marta came to warn Niko about something and will not leave until she does.",
  "reveals": "fact_marta_warning" }
```

- Kinds for v1: `approach` (walk until adjacent to the target), `follow` (stay within 2 tiles) and
  `visit` (go to a named point of interest, then stay).
- Movement goes through the same `move` action and rules as Niko. The path is a BFS over walkable
  tiles with a fixed neighbour order, so the same state always gives the same step.
- Status moves `active` → `arrived` (goal reached, now offers a conversation) → `done` (goal
  resolved). If the path is blocked, status becomes `blocked` and the NPC falls back to wander.
- The agenda step runs once per tick for each NPC with an `active` agenda, and uses no LLM call.

### 3.3 Conversation as an action

- A new `talk` action targets an adjacent NPC. It opens a `conversations` row and every following
  turn is a beat of that conversation until it closes.
- Each beat, the narrator returns the NPC's line and three options. The engine validates option
  ids as usual and discards invalid ones.
- A conversation closes when the player picks a leave option or `beat` reaches `maxBeats`
  (provisional: 4), whichever comes first. The engine, not the LLM, decides when it closes.
- On close, the engine marks the agenda `done` if the NPC's goal was delivered, stores the fact the
  agenda `reveals` in `facts_known` (once), and commits a `talked` event visible to its witnesses
  (which Dev-002 turns into memories).
- If an NPC with an `arrived` agenda is adjacent and the narrator did not offer `talk`, the engine
  replaces one option with it, so the player is never stuck without a way to engage.

### 3.4 Scene hook

- `data/scene.json` holds one open question for the opening scene (provisional: why Niko is in
  this house) and two or three facts that answer it, each revealed by one NPC agenda.
- The narrator prompt receives the question and only the facts Niko already knows. Unknown facts
  are never sent, so the model cannot leak them.

### 3.5 Narrator prompt and checks

The prompt rules change as follows:

- No tile counts or metres. The engine passes a proximity label (`adjacent` ≤ 1, `near` ≤ 3,
  `far` otherwise) and a direction word instead of numbers.
- Short sentences, at most two per narration, fast rhythm, no decorative text (the style asked for
  in the original brief).
- Do not restate what the previous three narrations already said; they are included in the prompt.
- End on pressure, a question or a visible choice. The three options must differ in intent.
- Include the current room name and the last move so transitions are not skipped. If
  `data/house_zone.json` has no room labels, add `rooms` rectangles to it.

Checks, run by the engine after each LLM reply:

- Reject a narration that matches a tile-count pattern (for example `\d+\s*(tiles?|metres?|m)\b`) or
  has token overlap (Jaccard) ≥ 0.6 with any of the last three narrations.
- On rejection, retry once with a stronger hint; if it fails again, accept the offline narration.
  The retry is capped to protect `SPEND_CAP_USD`.

## 4. Decisions

- **Decided (from brainstorming):** turn-based; Niko is the only controlled character; the LLM
  proposes and the engine decides; all LLM traffic goes through OpenRouter.
- **Proposed, needs approval:** NPC agendas are data-driven and deterministic, with no LLM for
  pathing or goal choice. Reason: zero cost and replayable with the seed.
- **Proposed, needs approval:** a conversation is capped at 4 beats and closed by the engine.
- **Proposed, needs approval:** one retry at most on a rejected narration. Alternative: no retry,
  fall back to offline immediately (cheaper, blander).
- **Proposed, needs approval:** the engine may inject a `talk` option when an NPC is adjacent and
  waiting. Alternative: rely on the narrator to offer it.
- **Proposed, needs approval:** proximity thresholds (1, 3), `maxBeats`, the 0.6 overlap threshold
  and the scene hook content are provisional and live in data.

## 5. What must not break

- The engine is the only writer of state; agenda, conversation and facts tables are written only by
  the engine.
- The single `Action` API: NPCs use `move` and `talk` like Niko; no actor gets a shortcut.
- The client never simulates. Options keep using keys 1-3; no client change is planned beyond
  showing the conversation text the state already carries.
- Determinism: pathing, agenda steps, option injection and overlap checks use no RNG and no
  wall-clock time; any randomness goes through `rngFor`.
- Reactions come from knowledge: an NPC reacts only to what it perceived, and the prompt never
  contains facts Niko does not know.
- Migrations stay append-only and apply on an existing `game.db`.
- Offline mode keeps working end to end, including a full conversation.
- `llm_calls` keeps logging every call, including retries.

## TL;DR

Give NPCs data-driven, deterministic agendas so they walk toward Niko with a purpose, turn `talk`
into a capped multi-beat conversation closed by the engine, add one scene hook whose facts are
revealed by those conversations, and make the narrator drop tile counts, avoid repeating itself and
end on pressure. Verified by the new agenda, conversation and narrator tests, `npm run check` and a
manual 20-turn replay.
